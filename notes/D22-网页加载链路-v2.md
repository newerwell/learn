## 3. 我的页面加载链路

1. 浏览器根据 localhost:63342 的地址访问本机开发服务器。是否复用连接，以及 DNS、连接阶段各耗时多少，截图没有提供详细证据。
2. 浏览器请求 index.html；这次截图中它返回 200，Size 为 15.1 kB，Time 为 12 ms。
3. 浏览器解析 HTML，建立页面内容结构；解析内联 CSS，计算颜色、尺寸和 Flex 排列，再完成布局与绘制。自己编写的这份源码不需要额外下载 CSS 文件。
4. 本次记录还出现 favicon、data SVG、脚本和 JSON 加载活动。根据 Initiator 可以看到两个 JSON 由 content_main.js 发起；不把这些活动都解释成自己页面的必要依赖。
5. IDE 的自动刷新 WebSocket 保持连接，用于接收后续变化。它持续 Pending，不表示主 HTML 没有完成加载。

以上是结合源码与截图解释的流程，并不代表已经从截图测出了每一步的耗时。

## 4. 本次的缓存观察

截图中没有出现 304。能看到一条 memory cache 记录，但它是 data:image/svg+xml 内嵌资源；这只能说明该条记录来自内存，不能证明 HTML 的 HTTP 缓存生效。

本次勾选了 Disable cache，不能用它来证明“第二次刷新因 HTTP 缓存而更快”。如果要做缓存对照，应取消勾选，清空记录，连续进行普通刷新，再查看 Status、Size，以及请求和响应的缓存相关头。

| 情况 | 是否向服务器验证或获取资源 | 内容从哪里来 |
|---|---|---|
| 新鲜的 HTTP 缓存直接命中 | 通常不需要发请求 | 浏览器本地缓存 |
| 协商缓存返回 304 | 发出条件请求，服务器返回 304 | 继续使用本地缓存中的内容，304 响应本身不携带资源正文 |
| 获取新的 200 响应 | 通过网络获取响应 | 本次响应正文 |

判断是否使用缓存，要结合 Size 和缓存标记，不能只看状态码 200。第一次和第二次加载可能因缓存、连接复用、服务端处理、扩展活动等因素而不同；第二次并不保证更快。本次没有采集第二次刷新耗时，不填写虚构的前后差值。

## 5. 我能据此回答什么

- 本次 Network 共记录 7 项，传输量与资源大小均显示 8.7 MB；这是浏览器整次记录的汇总。
- 最大、且已完成记录中耗时最长的是 content_main.js：4,274 kB、32 ms。自己页面的 HTML 文档显示 15.1 kB、12 ms。
- 页面源码没有引入外部 JS/CSS，不能据此认定自己的页面主动下载了一个 4 MB 脚本；需要看 Request URL 确认注入资源来源。
- 本次没有观察到 304；data URL 的 memory cache 不能替代普通 HTTP 缓存实验。
- WebSocket 的 Pending 表示连接还开着，不等于页面没有加载完成。
